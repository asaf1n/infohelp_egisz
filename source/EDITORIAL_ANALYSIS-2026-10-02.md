# Анализ руководства по интеграции с ЕГИСЗ и рекомендации по редактуре

Редакция от 02.10.2026. Объект анализа: рабочая редакция `docs/egisz/` (38 страниц без партиалов), связанные разделы `docs/services1/`, `docs/sync_manager/`, `docs/podderzhka/`, внутреннее дерево `internal/egisz/` (9 страниц), навигация `sidebars.ts` и `sidebarsInternal.ts`, методические документы `source/`, экспорт исходного руководства Notion в `work/`. Промпт для сессии редактирования вынесен в [EDITING_SESSION_PROMPT.md](EDITING_SESSION_PROMPT.md).

## Граница проверки

Проверено чтением исходников и сопоставлением с экспортом Notion и реестром расхождений [ONLINE_SOURCES.md](ONLINE_SOURCES.md). Сборка сайта, проверка ссылок в браузере и испытание процедур на МИС в этой проверке не выполнялись. Первоисточники практик (diataxis.fr, developers.google.com, learn.microsoft.com, sre.google, serviceinnovation.org, vale.sh) недоступны из сети текущей сессии; их положения приведены по ранее изученным редакциям и по уже закреплённым ссылкам в [DOCUMENTATION_STANDARD.md](DOCUMENTATION_STANDARD.md). Нормативные даты (приказ № 209н) не перепроверялись.

## Общий вывод

Руководство находится в состоянии, когда редакционный стандарт сформулирован лучше, чем выполнен. Стандарт требует одного места описания, нумерованных шагов с местом действия и признаком результата, отделения объяснения от процедуры и справочника, сохранения фактов источника. Текущие страницы в основном написаны связным языком и не содержат служебных заметок, но:

- навигация после реструктуризации от 28–29.09.2026 расходится с таблицей «Единое место описания» стандарта, и стандарт ссылается на несуществующие страницы;
- одна и та же информация повторяется в трёх-четырёх местах (задачи репликации, подготовка пакетов обновления, шаблон обращения, лицензии на эпикризы);
- при переносе из Notion потеряно не менее десяти конкретных фактов (OID справочников для проверки реквизитов, адреса проверочных ресурсов, пути настройки подписи, варианты формирования эпикриза);
- во внешнем руководстве есть материал, адресованный только сотрудникам СДС (внутренний файловый ресурс `sds-programs\trunk`, 236 ссылок на корпоративный Trac, цены);
- внутреннее дерево на две трети состоит из страниц-заглушек, а раздел «Другие интеграции» — полностью;
- отсутствует метаданные применимости (версия МИС, дата проверки, проверяющий), которые стандарт объявляет условием готовности страницы;
- нет инструментов автоматической проверки стиля и терминологии, поэтому однородность держится только на ручной вычитке.

Ниже даны находки и рекомендации в порядке: структура, редакционная вычитка, процесс и инструменты, порядок работ.

## Практики, на которые опираются рекомендации

Проект уже выбрал три опоры: Diátaxis для разделения типов содержания, правила процедур Google и Microsoft для шагов, подход Google SRE к плейбукам диагностики. Ниже перечислено, что из этих и смежных практик применимо к данному руководству и ещё не применено.

| Практика | Что добавляет для этого руководства | Статус в проекте |
|---|---|---|
| [Diátaxis](https://diataxis.fr/): tutorial, how-to, reference, explanation как разные формы с разными обязательствами перед читателем; how-to не обязан объяснять, reference не содержит процедур | Разделение страниц `semd/index`, `remd-iemk`, `settings/nsi`, где объяснение, процедура и справочная таблица смешаны | Зафиксировано в стандарте, выполнено частично |
| Правила процедур Google и Microsoft: вводная фраза с целью, один шаг — одно действие, место действия перед действием, признак результата после шага, точные имена элементов интерфейса | Единый шаблон шага для всех процедур; сейчас часть шагов без результата (`settings/departments`, `settings/employees`), часть страниц начинается с действия без постановки задачи (`connection/connection-process`) | Зафиксировано, выполнено частично |
| Google SRE, плейбуки: запись «симптом → проверка → действие → эскалация», короткая, обновляемая после каждого инцидента | Таблица «Быстрый переход по симптому» в `diagnostics/index` уже построена так; внутренних плейбуков по инцидентам нет | Выполнено для внешней диагностики |
| KCS (Knowledge-Centered Service): статья базы знаний создаётся в момент решения обращения и имеет фиксированную структуру — проблема, окружение, причина, решение; статья имеет состояние уверенности (черновик, проверена, опубликована); повторное использование важнее создания | Структура для `internal/egisz/knowledge-loop` и для будущих записей каталога ошибок; состояние «проверено на МИС» как поле страницы | Не применено |
| «Every Page Is Page One» (M. Baker): страница самодостаточна, называет контекст и применимость, ссылается на соседей вместо повторения | Уже требование AGENTS.md; нарушается там, где контекст даётся только на индексной странице раздела | Зафиксировано, выполнено частично |
| Docs-as-code: линтер стиля (Vale), markdownlint, проверка ссылок и орфографии в CI, шаблон PR с чек-листом, владельцы разделов | Автоматическая защита терминологии и стиля; сейчас есть только `onBrokenLinks: throw` при сборке | Не применено |
| Метаданные применимости (GitLab, Red Hat, Atlassian): «применимо к версии», «проверено», «владелец» в заголовке страницы | Стандарт требует версию МИС, дату проверки и проверяющего, но ни одна страница их не содержит | Не применено |
| Единый источник для повторяющегося содержания (DITA conref, Docusaurus partials) | Партиалы уже используются для параметров интеграции и подготовки пакетов; таблицы задач репликации, шаблоны обращений и сведения о лицензиях ещё дублируются текстом | Выполнено частично |

## Структура

### Расхождение стандарта и фактической навигации

Таблица «Единое место описания» в [DOCUMENTATION_STANDARD.md](DOCUMENTATION_STANDARD.md) ссылается на `setup/integration-parameters`, `testing/configuration-check`, `testing/support-request`, `egisz/setup/replication`, `egisz/setup/nsi`. После коммита 94c9fa0 эти пути заменены на `settings/`, `diagnostics/`, `connection/`. [STRUCTURE_MERGE-2026-09-12.md](STRUCTURE_MERGE-2026-09-12.md) описывает ещё одну, промежуточную структуру (`overview/`, `testing/`). Читатель стандарта не может найти названные им страницы. Рекомендация: обновить таблицу стандарта под текущие пути и зафиксировать правило, что любая реструктуризация сопровождается правкой этой таблицы в том же коммите.

### Порядок разделов не совпадает с маршрутом читателя

Индексная страница задаёт маршрут: порядок подключения → требования → настройка → подключение видов СЭМД → чек-лист проверки → тестовая отправка → эксплуатация. В меню этот маршрут разорван: «СЭМД» стоит после «Диагностики», «Чек-лист проверки» находится в «Диагностике», «Тестовая отправка» — в «Подключении интеграции», а «Подключение интеграции» не имеет индексной страницы, в отличие от остальных категорий. Три справочные страницы (`remd-iemk`, `terminology`, `normative-bases`) лежат на верхнем уровне без группировки.

Предлагаемый порядок меню (перемещение файлов не обязательно, достаточно `sidebars.ts`):

| Категория | Страницы | Тип по Diátaxis |
|---|---|---|
| Модуль «Интеграция с ЕГИСЗ» | `index` | Вход по задаче |
| Об интеграции | `remd-iemk`, `terminology`, `normative-bases` | Объяснение, справочник |
| Подключение | `connection/connection-process` (индекс категории), `connection/technical-requirements` | Процедура, требования |
| Настройка | `settings/*` в текущем порядке | Процедуры |
| СЭМД | `semd/connection`, `semd/protocol-configuration`, `semd/profiles`, `semd/index` как справочник, `semd/catalog` | Процедуры и справочник |
| Проверка и тестовая отправка | `diagnostics/check-list`, `diagnostics/sql-configuration-check`, `connection/test-integration` | Процедуры приёмки |
| Эксплуатация | `operation/*` | Процедуры, справочник статусов |
| Диагностика | `diagnostics/index`, `diagnostics/error-catalog`, `diagnostics/support-request` | Плейбук, справочник |
| Другие интеграции | только после появления содержания | — |

Основание: этап «проверка готовности» в стандарте и в индексной странице существует как отдельный шаг маршрута, а в меню его нет; чек-лист при этом нужен и при внедрении, и при диагностике, поэтому ему место в этапе приёмки со ссылкой из диагностики.

### Граница внешнего и внутреннего

Во внешнем дереве присутствуют сведения, адресованные сотрудникам СДС:

- партиал `_initial-preparation` указывает хранилище `sds-programs\trunk\` и порядок установки пакетов; читатель МО не имеет к нему доступа, но страница `diagnostics/index` предписывает это действие «перед диагностикой любой ошибки»;
- `settings/nsi` содержит семь ссылок на `corp.sdsys.ru/trac` и таблицы сопоставления на уровне полей `DICINFODET`, `DICINFO.rekvint*`, то есть инструкцию для специалиста внедрения, а не для сотрудника МО;
- `semd/catalog` содержит 228 ссылок на Trac и цены эталонных протоколов; по [WORK_PLAN-2026-09-12.md](WORK_PLAN-2026-09-12.md) это решение владельца стенда для тестовой среды, но для публикации оно требует пересмотра;
- `remd-iemk` называет стоимость лицензии в рублях; цена устареет раньше, чем текст, и её место в коммерческом документе.

Рекомендация: до публикации разделить `settings/nsi` на внешнюю часть (какие справочники нужны, как проверить загрузку, сопоставление через интерфейс МИС) и внутреннюю (сопоставление через таблицы БД, ссылки Trac); партиал подготовки пакетов перенести во внутреннее дерево, во внешней диагностике заменить его фразой «убедитесь, что установлены актуальные обновления федеральных сервисов; при сомнении обратитесь в поддержку». Для каталога СЭМД заготовить второй вариант без цен и ссылок, как уже делалось 13.09.2026, и выбирать при сборке.

### Страницы без содержания

- `other-integrations/*`: четыре страницы, три из которых состоят из одной фразы «В этой справке нет процедуры». Они попадают в поиск и меню и создают впечатление раздела. Рекомендация: убрать категорию из `sidebars.ts` до появления содержания, оставив одну страницу-заглушку с перечнем интеграций и ссылкой на действующую справку.
- `internal/egisz/database`, `deep-diagnostics`, `knowledge-loop`, `corporate-resources`: страницы существуют, чтобы сообщить об отсутствии содержания. Рекомендация: свернуть во внутренний индекс как разделы с явной пометкой ограничения; восстановить как страницы, когда появятся процедуры.
- `podderzhka/index`: две фразы, обе дублируют `diagnostics/support-request`. Рекомендация: объединить с внутренним регламентом или удалить из меню.

### Версии

`versioned_docs/version-26.1` содержит снимок прежней структуры (`overview/`, `preparation/`, `setup/`, `testing/`, `troubleshooting/`), `version-25.2` — одну страницу. Переключатель версий показывает их читателю наравне с рабочей редакцией, а локальный поиск индексирует все версии. [AUDIT-2026-09-12.md](AUDIT-2026-09-12.md) уже указывал, что это демонстрационные снимки. Рекомендация: удалить `versions.json` и снимки до первого реального выпуска, оставив одну редакцию без переключателя; восстановить версионирование, когда появится вторая поддерживаемая версия МИС с отличающимся содержанием.

### Ссылки и якоря

В `docs/` и `internal/` 47 ссылок заданы абсолютным путём `/trunk/...` и 213 — относительным путём к файлу `.mdx`. Абсолютные ссылки жёстко привязаны к `path: 'trunk'` рабочей редакции: при создании снимка версии они продолжат вести в trunk, а при переименовании маршрута сломаются. Рекомендация: использовать только относительные ссылки на файлы; ссылки из `internal/` в `docs/` оставить абсолютными, так как это разные плагины, и описать это исключение в стандарте.

Якоря на кириллические заголовки (`#этап-1-проверка-запроса-на-регистрацию`, `#время-ожидания`, `#контроль-иэмк`) используются в 14 местах, явные идентификаторы `{#id}` — в четырёх. Якорь по тексту заголовка ломается при любой правке заголовка. Рекомендация: для заголовков, на которые есть ссылки, задавать явный латинский идентификатор.

### Метаданные страницы

Используются только `id`, `title`, `sidebar_label`, `description`; 15 страниц служебных модулей не имеют `description`, хотя локальный поиск и карточки навигации его используют. Стандарт требует для готовой страницы версию МИС, дату проверки и проверяющего, но места для них нет. Рекомендация: ввести поля фронтматтера `applies_to` (версия МИС или компонента), `verified` (дата), `verified_by` (роль, не имя) и `status` (`draft`, `reviewed`, `tested`), выводить их компонентом в начале страницы и использовать `status` при сборке публичного выпуска. Это переносит условие готовности из методического документа на саму страницу и даёт поиску сигнал о степени доверия.

## Редакционная вычитка

### Факты, потерянные при переносе из Notion

AGENTS.md требует не удалять факты и ограничения источника. Сопоставление с экспортом в `work/` показало отсутствие в текущей редакции следующих сведений:

| Сведение из Notion | Где должно быть | Примечание |
|---|---|---|
| OID справочников ФНСИ для проверки реквизитов: организации `1.2.643.5.1.13.13.11.1461`, должностей `1.2.643.5.1.13.13.11.1002`, подразделений `1.2.643.5.1.13.13.99.2.114` | `settings/organization`, `settings/employees`, `settings/departments` | Сейчас дана общая ссылка «НСИ ФРМО» без указания справочника |
| «Значения переносятся из ФРМО и ФРМР без начальных и конечных пробелов и нечитаемых символов» и следствие «Расхождение реквизитов … приводит к отказу в регистрации» | `settings/index` или начало каждой страницы реквизитов | Это связь действия с причиной, которую AGENTS.md требует сохранять |

### Изменение SQL относительно источника

В `diagnostics/sql-configuration-check.mdx` проверки 12–14 возвращают кириллическое `'ОК'`, тогда как в Notion и в снимке `versioned_docs/version-26.1` они возвращают латинское `'OK'`. Замена произошла в коммите 94c9fa0 вместе со структурной правкой и не отражена в описании. Прежняя страница объясняла различие и предупреждала о нём; теперь объяснение удалено, а текст запроса отличается от файла `egisz-check.sql`. Если замена сделана намеренно, нужно обновить исходный файл и зафиксировать это в [ONLINE_SOURCES.md](ONLINE_SOURCES.md); если нет, вернуть исходный текст и предупреждение. Стандарт прямо указывает, что SQL из источника не изменяется редактурой.

### Замечания по страницам

Перечислены отклонения от AGENTS.md и стандарта, которые влияют на выполнение задачи читателем.

- `connection/connection-process`: страница начинается с указания «укажите OID, сервисы и перечень видов СЭМД» без постановки задачи и без указания, где это указать. Нужен вводный абзац: что такое подключение, кто участвует, что получится в конце.
- `connection/technical-requirements`: первая фраза отсылает к `docs.sdsys.ru/tech` и `docs.infoclinica.ru`; в Notion требования привязаны к приложению № 5 договора. Происхождение ссылок не зафиксировано в реестре источников. Фраза «кроме случаев из пункта 13 Порядка» не определяет, какого Порядка. Раздел «Электронная подпись» по типу — объяснение внутри страницы требований; процедура настройки подписи отсутствует.
- `connection/test-integration`: шаги 2 и 3 описывают два подписания («оформите и подпишите протокол», затем «сформируйте и подпишите СЭМД»), тогда как по архитектуре СЭМД формируется при подписании протокола. Снимок экрана настройки шаблонных протоколов стоит после шагов без привязки к какому-либо шагу.
- `settings/departments`, `settings/employees`, `settings/organization`: процедуры не называют признак результата и не говорят, к чему приводит расхождение с ФРМО/ФРМР. В `departments` заголовок говорит «Подразделения», шаги — о финподразделениях.
- `settings/integration-parameters`: UUID и код РМИС приведены как константы без пояснения, что это идентификаторы портала «Инфоклиника.RU», единые для всех клиник; читатель может принять их за значения, которые нужно получить. Раздел «Доверенное подключение между базами данных» и SQL на `settings/iemk`, `settings/remd` не соответствуют требованию стандарта к изменяющим БД инструкциям: нет СУБД и версии, прав, условий повторного запуска и восстановления; в `remd` значения `filial`, `grpid` жёстко заданы без объяснения. Фраза «перезапустите МИС» не уточняет, что перезапускается.
- `settings/nsi`: на одной странице объяснение, процедура загрузки, восемь процедур сопоставления и две справочные таблицы уровня БД. Предупреждение о наименовании договора не объясняет причину. Ссылки на Trac во внешнем документе.
- `semd/index`: заголовок «Структурированный ЭМД», метка меню «СЭМД», содержание — объяснение, две справочные таблицы и процедура «Что проверить перед подключением». Процедуру перенести в `semd/connection`, таблицы оставить справочником.
- `semd/connection`: описание страницы обещает алгоритм «лицензия → профиль → протокол → параметры → НСИ → тестирование», но страница содержит три абзаца и таблицу состава работ без нумерованных шагов. Стандарт запрещает описания, не соответствующие содержанию.
- `semd/protocol-configuration`: снимки экрана стоят между пунктами нумерованного списка на нулевом отступе; в Markdown это разрывает список, нумерация держится только на явных номерах. Снимки нужно сдвинуть внутрь пункта.
- `semd/catalog`: 2 775 строк, 228 раскрывающихся блоков с одинаковой структурой. Страница не сканируется и утяжеляет индекс поиска. Данные хранить как JSON или CSV в `src/data/` и рендерить таблицей с группировкой по статусу; это также упростит сборку варианта без цен и ссылок.
- `remd-iemk`: последовательность обмена приводится без оговорки, хотя [ONLINE_SOURCES.md](ONLINE_SOURCES.md) фиксирует открытый вопрос о порядке запроса документа. Два раздела об эпикризах ИЭМК повторяют друг друга.
- `diagnostics/error-catalog`: хорошая структура по этапам; требуется единая форма действий в столбце и расшифровка сокращений.
- `operation/faq`: ответы ссылаются на нужные страницы; раздел уместен, но два вопроса («SQL не выявил ошибок», «справочник загружен, но значения нет») дублируют строки таблицы симптомов в `diagnostics/index`.
- `internal/egisz/escalation-to-development`: заголовок «Если проверка не пройдена» вводит раздел, который описывает условие передачи, а не действие при провале; `support-process` описывает роли и процесс, но после удаления SLA «Сроки обработки» не содержит сведений.
- `versioned_docs/version-26.1/*`: содержит старые утверждения (гарантии валидации, срок 24 часа), которые читатель видит через переключатель версий.

## Процесс и инструменты

### Шаблон страницы

Ввести шаблоны для трёх типов страниц и хранить их в `source/templates/`:

- процедура: задача и результат → применимость и исполнитель → предварительные условия → нумерованные шаги (место, действие, признак результата) → проверка результата → действия при отклонении → связанные материалы;
- справочник: назначение → таблица → примечания об ограничениях → где используется;
- объяснение: что это → как устроено → границы и ограничения → куда идти дальше.

Диагностическая запись (плейбук, статья базы знаний) по KCS: симптом в формулировке пользователя → окружение (версия МИС, сервис, вид СЭМД) → как подтвердить → причина → действие → как проверить, что помогло → когда эскалировать. `diagnostics/error-catalog` и будущие записи `internal/` строить по этой схеме.

### Линтеры и проверки в CI

Сейчас единственная автоматическая проверка — сборка с `onBrokenLinks: throw`. Рекомендуемый минимум:

1. `markdownlint` для структуры Markdown (один H1, последовательность заголовков, отступы списков, пустые строки вокруг таблиц).
2. Vale с собственным набором правил на русском: подстановки терминов из глоссария (`Статусы передачи → Статусы обмена`, `шлюз → ИПС ЕГИСЗ`), запрет слов-маркеров истории («раньше», «теперь», «уже добавлено», «по уточнению», «в предоставленных материалах»), запрет инфинитива в начале шага, предупреждение на сокращения, отсутствующие в глоссарии. Vale не зависит от языка: правила типа `existence`, `substitution`, `occurrence` работают на регулярных выражениях.
3. Проверка орфографии на русском (LanguageTool или yaspeller) с пользовательским словарём терминов.
4. Скрипт проверки фронтматтера: обязательные `description`, `applies_to`, `status`; длина `description`.
5. Скрипт проверки абсолютных ссылок `/trunk/` внутри `docs/`.
6. `npm run build` дважды, как уже принято в README.

Глоссарий вести как один файл данных (`source/glossary.yml`: термин, определение, допустимые формы, запрещённые синонимы) и генерировать из него и страницу `terminology`, и правила Vale. Это убирает расхождение между глоссарием и текстом.

### Процесс правок

- Шаблон PR с чек-листом из раздела «Редакторская проверка» стандарта и строкой «затронутые страницы перечитаны отдельно от соседних».
- Правило одного коммита на одно изменение смысла: структурные перемещения и правки содержания не смешивать (пример: коммит 94c9fa0 изменил SQL вместе с перемещением страниц, и изменение не было замечено).
- Запись в `ONLINE_SOURCES.md` для каждого факта, добавленного не из Notion, Google-документа или официальной справки, с датой и источником; сейчас так оформлены не все внешние ссылки.
- Контрольные задания из стандарта (найти причину отсутствия значения НСИ, проверить статус документа, подготовить обращение) выполнять на каждой крупной редакции и фиксировать результат в `source/`.

## Порядок работ

1. Синхронизировать стандарт с текущей структурой; выбрать термины по таблице выше и внести в глоссарий; ввести поля применимости в фронтматтер. Это условие для всего остального, иначе правки разойдутся.
2. Вернуть потерянные факты из Notion по таблице выше и разобрать изменение SQL. Это восстановление источника, не редактура.
3. Устранить дублирование: задачи репликации, подготовка пакетов, шаблон обращения, эпикризы ИЭМК.
4. Пересобрать меню по маршруту читателя; убрать пустые категории и демонстрационные версии.
5. Разделить внешнее и внутреннее содержание (`settings/nsi`, партиал подготовки пакетов, каталог СЭМД).
6. Пройти страницы по чек-листу промпта в порядке маршрута подключения: подключение → настройка → СЭМД → проверка → эксплуатация → диагностика.
7. Подключить линтеры и глоссарий как данные; закрепить шаблон PR.

Пункты 1–3 можно выполнить одной сессией редактирования с промптом из [EDITING_SESSION_PROMPT.md](EDITING_SESSION_PROMPT.md); пункты 4–5 требуют решения владельца о границе публикации; пункт 7 — отдельная техническая задача.
