# Аудит стенда и решения по документации ЕГИСЗ

Проверка от 12.09.2026. Объект: `C:\Users\artem\InfoHelp_local`, исходный адрес `http://localhost:3006/`, отчёт Claude из приложенного файла. Основной источник содержания — Notion, согласно решению пользователя в ходе аудита.

## Вывод

В проекте создан отдельный Docusaurus-стенд раздела ЕГИСЗ. Полной копией действующей веб-справки он не является: в исходниках присутствуют только новый раздел, внутренние материалы и демонстрационные версии. Первоначально контейнер работал, но сайт был неработоспособен из-за восьми ошибок компиляции.

Стек следует сохранить. Основная работа — завершение и проверка содержания, а не смена генератора сайта. На рабочем маршруте `/trunk/egisz/` подготовлены основные страницы внедрения и поддержки. Это рабочая редакция, которая ещё не прошла испытание процедур на МИС.

## Оптимальное решение

| Вариант | Оценка для этого проекта |
|---|---|
| Сохранить Docusaurus и завершить текущую структуру | Рекомендуется: уже есть исходники, Markdown/MDX, ручное меню, диаграммы, версии и сборка. Выявленные технические проблемы локальны и исправимы |
| Перенести всё в другой генератор или CMS | Сейчас перенос потребует повторной настройки и проверки маршрутов; пробелы содержания останутся. Оснований для смены стека аудит не выявил |
| Использовать только Notion | Подходит как основной источник и место обсуждения редакции; для поставляемой версии веб-руководства предлагается фиксировать согласованный текст в репозитории |

Рекомендация основана на наблюдаемом состоянии проекта, а не на сравнительном тестировании всех платформ. Для навигации сохранить этапы внедрения, добавить вход по задаче и симптому, общие параметры хранить в одном месте. Содержание инструкций строить по [Diátaxis](https://diataxis.fr/) и [правилам процедур Google](https://developers.google.com/style/procedures); структуру диагностики — по [Google SRE](https://sre.google/workbook/on-call/). Подробное применение этих практик описано в [DOCUMENTATION_STANDARD.md](DOCUMENTATION_STANDARD.md).

Не создавать реальный снимок каждой версии МИС автоматически. По [документации Docusaurus](https://docusaurus.io/docs/versioning), версионирование увеличивает стоимость сопровождения; оно оправдано, когда действительно требуется поддерживать различающееся содержание. Перед утверждением выпуска нужны совместимость с конкретной МИС и проверенный набор процедур.

## Разделение публичных и внутренних материалов

Два docs-plugin и путь `/internal` не обеспечивают контроль доступа. Сейчас всё попадает в одну статическую сборку и поиск. Ограничение Docker-портов адресом 127.0.0.1 соответствует локальному назначению стенда.

Для публикации следует выпускать отдельные публичную и внутреннюю сборки с отдельными индексами поиска. Внутреннюю сборку размещать за корпоративной авторизацией. Скрытие пункта меню, robots.txt или пометка internal не защищают файлы. Docusaurus формирует статические файлы, а доступ контролируется инфраструктурой размещения — см. [Deployment](https://docusaurus.io/docs/deployment).

## Нерешённые вопросы и порядок завершения

1. Согласовать расхождения из [ONLINE_SOURCES.md](ONLINE_SOURCES.md), прежде всего состав подписей, параметры задач, правила повторной отправки и актуальные нормативные основания.
2. Получить перечень реально поддерживаемых СЭМД с редакциями и эталонные настройки. Национальные справочники не заменяют матрицу поддержки МИС.
3. Завершить процедуры настройки ИЭМК/РЭМД и филиальной сети, проверить повторный запуск SQL на тестовой БД. До этого не публиковать команды изменения БД как готовые рецепты.
4. Выполнить один полный сценарий внедрения и сценарии обработки ошибок независимым специалистом; сохранить результаты и исправить инструкции.
5. Подтвердить владельцами внутренние регламенты, SLA и порядок эскалации. Подготовить выпуск и карту переходов со старых URL действующего портала.

## Техническая проверка

Окончательная конфигурация проверена после исправления языка поиска, баннеров версий и расположения диаграммы:

- `docker compose exec -T dev npm run typecheck` — код завершения 0.
- `docker compose exec -T build sh -c 'npm run build && npm run build'` — обе последовательные сборки успешны, общий код 0. Проверки ссылок и якорей остались в режиме `throw`.
- `docker compose config --quiet` и `git diff --check` — без ошибок.
- В браузере на 3006 больше нет перекрывающего страницу сообщения о восьми ошибках компиляции. Генерируемый файл внутри dev-контейнера не содержит Windows-путей.
- На 3007 проверен поиск `callback`: выдаёт страницу параметров и переходит на неё. Поиск `СНИЛС` выдаёт соответствующие страницы. Выдача включает и незавершённые страницы — они помечены при открытии; настройка качества ранжирования остаётся отдельной задачей.
- Проверены переключатель версий и переход в макет 25.2; после уточнения текста он ссылается на рабочую редакцию.
- Mermaid создаёт SVG; вертикальная схема просмотрена в браузере, подписи читаются при обычном масштабе.
- Корень, рабочая редакция, снимок 26.1, макет 25.2, внутренний раздел и страница параметров доступны по HTTP на 3007. На 3006 корень и маршруты рабочей редакции/internal отвечают 200 при запросе HTML.
- В проверенной вкладке статической сборки ошибок JavaScript не зарегистрировано.

Оба контейнера оставлены работающими. Пересборка preview временно удаляет старое содержимое `build/site`; во время сборки возможен ответ 404. Проверять страницы следует после сообщения `Generated static files`. Для обычного просмотра используйте [собранное руководство](http://localhost:3007/trunk/egisz/), для редактирования — [dev-стенд](http://localhost:3006/trunk/egisz/).

Проверка не включала выполнение SQL на МИС, передачу документов в ЕГИСЗ, испытание электронных подписей, полный обход внешних ссылок или полный аудит доступности интерфейса. Новые материалы не публиковались на help.infoclinica.ru, в Notion или Google Docs.
